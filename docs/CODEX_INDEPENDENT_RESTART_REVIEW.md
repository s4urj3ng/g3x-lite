# Codex independent restart review — Canon PowerShot G3 X GM1.10C

Review/retrieval date: **2026-10-25 (Asia/Seoul)**. Reviewer: Codex, independent adversarial reviewer.
Repository: [s4urj3ng/g3x-lite](https://github.com/s4urj3ng/g3x-lite), local HEAD `932371663b61aacaeca8b67106ccfce62a8cce02`, with pre-existing uncommitted/untracked material. The source register below identifies the actual local inputs; HEAD alone does not identify every input.

**Verdict: INSUFFICIENT EVIDENCE. Hardware readiness remains NOT READY / STRICT NO-GO.**

The strongest supported concern is a mismatch between newly initialized software and inherited hardware: `boot()` erases the IRQ handler table, but the documented controller writes have no independently established enable/pending/reset semantics. Neither a safe restart nor an inevitable IRQ failure follows from the available evidence.

The strongest contradiction in the readiness narrative is that PORT-3C describes SD1stInit executing CMD0 and storage mounting cleanly, whereas its underlying SD audit records conditional execution and explicitly leaves restart-path CMD0 reachability unproven. Restoring a task-creation call does not close that gap.

## 1. Scope, method, and classification

This is an evidence review, not an implementation or deployment review. No firmware/source/test changes, builds, test-suite execution, camera/SD-card operations, MMIO probing, flashing, deployment, commits, pushes, or PR operations were performed. Only this report and the repository-required state/handoff entries are documentation outputs.

PORT-3B §4 explicitly records two classifier-stopped investigations: IRQ API caller/line enumeration and SD register-write-site enumeration. Neither was repeated, reframed as a narrower call-tree task, or continued. PORT-3C §9's proposal is not an authorized next action for this review.

Evidence checks were deliberately bounded:

- Read the requested audits, current state/handoff and safety/protocol documents, isolated prototype source, and relevant test/validator source.
- Hashed the local ROM: **33,554,432 bytes**, SHA-256 `9911855772e433c877a9914f16d3735e15a48ca63352633e8f10364182912578`, matching the documented image identity. This does not independently establish dump provenance or camera state.
- Parsed only literal `ROM_BYTES`, `ROM_WORDS`, and mapping constants from the existing IRQ and SD tests using Python `ast.literal_eval`; compared those fixed pins with the local ROM without importing/running the tests. IRQ: **25 byte-sequence + 12 word comparisons matched**. SD: **19 + 9 matched**. Total: **65 matches**, not 65 runtime tests.
- Re-read only the already documented task-wrapper (`0xBFE11722..0xBFE11732`) and IRQ-unmask helper (`0xFC267BE6..0xFC267BF6`) with already installed Capstone 5.0.7. No caller search or register-write enumeration was involved.
- Read source-level witness behavior and snapshotted protected artifacts for an end-of-review identity comparison. No new source-to-binary build equivalence is claimed.

**VERIFIED** means the stated static property is directly supported by inspected source/fixed ROM anchors or a specifically identified recorded trace. **PLAUSIBLE** means compatible with the evidence but dependent on an incomplete trace, analogy, or hardware inference. **UNKNOWN** means a necessary premise is missing. **CONTRADICTED** means the claim, as stated, conflicts with an identified source; it does not imply every stronger or weaker version is false. A verified instruction sequence is never labeled a verified physical outcome.

## 4. Independent alternative assessment

Two materially different hardware interpretations remain compatible with the same recorded instructions:

1. The undocumented controller init writes could suppress inherited enables or otherwise prevent delivery until handlers are restored. This would make the principal IRQ concern less severe. Their semantics have not been proven; lack of a bulk by-ID disable does not refute this interpretation.
2. The writes could clear some other attribute or only pending status, while a peripheral can later assert with no registered handler. This makes the documented panic path relevant. No supplied observation establishes that this actually happens.

Neither interpretation wins from the ROM access pattern alone. The defensible conclusion is an unresolved necessary safety premise, not a demonstrated inevitable brick or a demonstrated safe restart. Likewise, adding the SD creator can correct a static omission while leaving execution, host normalization and command completion unknown. The remaining problem is evidence of hardware-state convergence, rather than merely finding another missing call.

The earlier architectural preference for restart is not a safety proof. [PORT-2C decision §§2–4 (local-only, untracked: docs/CHDK_PORT2C_ARCHITECTURE_DECISION.md:24)] describes a particular non-restart layout that overlaps the stock heap. That is a reason to reject that layout; it does not prove every non-restart design impossible or make restart safe by elimination. The “100% of ports” and field-reliability claims have no independently checked inventory/runtime record in this review. Sister-port creator calls provide a plausible implementation precedent, not GM1.10C silicon equivalence. No alternative implementation is proposed.

PROJECT_STATE's historical native-payload/UI hardware results concern execution within an already running Canon environment. Those reported observations do not independently establish this warm-restart path, recreated scheduler/handler state, or post-restart SD recovery.

PORT-3C also treats several CPU/MPU/cache properties as fully satisfied runtime preconditions. The sources support instructions, selected layout bounds, and recorded configuration traces; they do not constitute physical observation that all inherited bus/CPU/peripheral state converges. Source annotations themselves disagree on Cortex-A9 versus Cortex-R4 (`boot_prototype.c` header, inspector assembly and reproducibility target flags). This review does not settle silicon identity from comments/compiler flags or assume an active secondary core. Such inherited-state assumptions remain conditional and cannot improve the verdict.

## 7. Decision and handoff

**Final verdict: INSUFFICIENT EVIDENCE** for the feasibility of a *safe* GM1.10C CHDK-style warm restart; **NOT READY** for hardware execution. The architecture is plausible, a conditional IRQ failure mechanism is supported, and successful continuation/storage recovery is not independently demonstrated. The supplied evidence establishes neither inevitable failure nor safe boot.
